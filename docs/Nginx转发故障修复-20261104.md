# Nginx 转发故障修复 · 2026-11-04

## 实际链路与根因

小程序使用 `https://www.myhaibin.top/new-api`，Nginx 将照片业务 `/api/user/`、`/api/photo/`、`/api/history/`、`/api/app/` 转发到 `http://1ln0498ig7766.vicp.fun:58079`。本轮没有改为小程序直连隧道。

14:16 实测公网配置接口 HTTP 502，而服务器及本机直接访问远端配置接口均为 HTTP 200、业务 code 200。Nginx 错误日志显示登录仍连接 `222.129.39.161:58079` 并被拒绝；系统和服务器 DNS 解析的当前地址为 `222.129.32.82`。根因是静态 upstream 保留了启动时的旧 IP。

`/shiguang-api` 此时仍返回海滨管理页面 HTML，是未上线的迁移方案，不能作为当前 API 地址。此前文档的“当前配置”表述已更正。

## 已实施的服务器修复

- Nginx 1.24.0：四组照片路由使用变量形式 `proxy_pass`，配合服务器已有 DNS `183.60.83.19`、`183.60.82.98`，设置 `valid=60s ipv6=off`。
- `rewrite ^/new-api/(.*)$ /$1 break` 剥离公网前缀；保留请求参数、方法、正文及既有代理请求头。
- 增加 `/new-api/api/member/` 的远端转发，避免会员请求落到本机海滨服务。远端会员接口尚未部署，仍返回 404。
- 修改仅涉及上述照片业务路由；海滨 `/new-api/` 通用路由、管理端、MinIO 及其他代理配置保留。
- 候选配置和切换前配置均通过 `nginx -t`，14:19 平滑 reload。配置备份在服务器：`/usr/local/nginx/conf/nginx.conf.before-shiguang-dns-20261104-141900`。
- 候选配置、原配置校验值及备份保留在服务器内；没有下载完整 Nginx 配置到本机。

实现依据：[Nginx proxy_pass 变量域名解析与 URI 规则](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)。Nginx 1.24 开源版本不使用 upstream `server ... resolve`，该功能在 1.27.3 之前仅商业版本提供，参见[官方 upstream 文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server)。

## 验证结果

- 公网配置接口恢复 HTTP 200 / code 200，超过 DNS 缓存周期后复测仍正常。
- 登录路由只读 GET 返回后端 405；缺参数作品列表返回后端 400，说明路径正确到达 Java 服务，不把这些响应当作业务成功。
- 14:20:24、14:20:28 小程序真实 `POST /new-api/api/user/login` 返回 HTTP 200；随后只读运行时检查确认 `hasLogin=true`。没有输出 openid 或凭证。
- 使用真实登录用户查询 `/api/user/usage` 与 `/api/history/list`，均返回 HTTP 200 / 业务 code 200；未读取或输出照片内容。
- `/actuator/health` 为 200 / UP；`/new-api/admin-ui/index.html` 为 200，海滨服务未受影响。
- 路由回归测试、App JS 语法和 `git diff --check` 通过。

## 剩余问题

远端 `/api/member/status` 直接访问也是 404；真实登录未返回 `sessionToken`。当前远端运行版本不具备工作区的新会员/会话接口，需在实际运行远端 Java 的机器上完成配套部署与数据库迁移。本轮未部署 Java、未改数据库、未绕过会员或保存认证。

真实上传、换底色及写入保存本轮未执行；此前保存接口 HTTP 500 的应用层问题不能用本次转发恢复替代验证。已询问远端服务机器的运行位置和连接方式，以便继续核对部署。
