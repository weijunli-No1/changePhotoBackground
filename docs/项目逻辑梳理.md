# 项目逻辑梳理

梳理日期：2026-10-22。基于 main 分支提交 `2b73716` 的静态代码阅读；未启动微信开发者工具，也未连接微信、MySQL、MinIO 或 Python 服务。以下区分当前实现与需要联调确认的行为。

本文件记录初始代码基线。后续广告接入修复、实际广告位、回归测试和待讨论的 Skyline 重构方向见 [界面重构方案](界面重构方案.md)；下方问题列表不代表所有问题仍未修复。

## 1. 产品范围与架构

当前产品是 AI 证件照微信小程序：选照片、自动抠图裁切、换背景色、保存单图、生成六寸排版照、查看历史作品，通过激励广告增加保存额度。

| 模块 | 实现 | 职责 |
| --- | --- | --- |
| 小程序 | `mini-program/`，原生 JS/WXML/WXSS + TDesign | 选图、编辑交互、预览、登录、广告、相册保存 |
| Java 后端 | `backend/`，Spring Boot 2.7.18 / Java 8 / MyBatis-Plus | 微信登录、内容检查、调用 AI、配额、历史记录、对象存储 |
| 图像服务 | 外部 HivisionIDPhotos，当前仓库不含其运行代码和模型 | 人像抠图与裁切、合成底色、生成排版照 |
| MySQL | `database/init_schema.sql` | 用户、照片历史、每日用量 |
| MinIO | `MinioStorageServiceImpl` | 保存成品文件，返回可直接访问的 URL |

小程序使用 Skyline 渲染器、glass-easel 组件框架、自定义导航栏和 TabBar；支持随系统切换深浅主题，样式变量主要在 `app.wxss` 和 `theme.json`。

当前没有管理端、支付订单、套餐或会员模块。`api_CN.md` / `api_EN.md` 描述的是 Python 图像服务能力，其中水印、KB 调整、独立裁切等尚未接入当前小程序和 Java 接口。

## 2. 页面与状态

| 入口 | 核心行为 |
| --- | --- |
| `app.js` | 恢复本地 openid，拉取广告位配置，提供 `doLogin()` |
| `pages/index/` | 从相册或相机选一张原图，将本地路径传给编辑页 |
| `pages/edit/` | 承担整条制作链路；保存原图路径、透明底 Base64、着色后 Base64、当前尺寸和颜色 |
| `pages/history/` | 登录后读取全部历史，按创建时间倒序展示，可预览、单条删除 |
| `pages/profile/` | 手动登录、退出、本地缓存清理、协议入口、微信客服入口 |
| `pages/document/` | 展示代码内写死的隐私政策和用户须知 |

图片处理中间态只保存在编辑页内存，没有草稿存储或跨页恢复。网络请求直接写在页面里，没有统一请求封装。

## 3. 登录流程

1. 启动时读取本地缓存的 openid；存在即按已登录展示，不进行会话有效性检查。
2. 用户在“我的”点击登录，前端调用 `wx.login()` 取得 code。
3. Java `/api/user/login` 通过 WxJava 调微信换取 openid。
4. 按 openid 查用户，不存在则注册，返回用户实体。
5. 前端缓存 openid，后续直接用它作为保存、历史查询和广告记录的用户标识。

当前没有服务端 Token、登录拦截器或资源归属校验体系。退出登录只清除本地标识。

## 4. 照片制作流程

1. 首页 `chooseImage()` 选取单张原图，进入编辑页，默认一寸、白底。
2. 编辑页 `processTransparentImage()` 上传原图及目标宽高到 `/api/photo/generate-idphoto`。
3. Java 为内容检测创建临时 JPEG，最长边缩放到不超过 800 像素；可选调用自定义 NSFW，再调用微信图片检查。
4. 检测明确判违规则返回错误；检测服务异常通常只记录日志，继续图像处理。
5. Java 将原始上传文件转发给 Python `/idphoto`，请求 `hd=true`，传入目标宽高。
6. 前端优先选 `image_base64_hd`，没有时使用标准图；去除 Base64 前缀和空白后存入 `transparentBase64`。
7. 自动调用 `/api/photo/add-background`；Java 转发到 Python `/add_background`，返回成品写入 `coloredBase64` 并预览。
8. 修改尺寸会重新上传原图并抠图。修改颜色复用透明图，仍请求服务器合成；自定义色盘有 200ms 防抖，换色响应用请求序号过滤旧结果。

预设尺寸：一寸 295×413、二寸 413×579、小一寸 260×378、小二寸 390×567。当前优先使用高清图，不能仅凭这些预设认定最终导出像素就是该宽高，需结合实际 Python 返回联调确认。

## 5. 保存、广告与配额

### 单图

前端要求已登录 → `/api/history/save` → 查用户与当日配额 → Base64 上传 MinIO → 写历史记录 → 增加保存次数 → 前端把 Base64 写入临时文件 → 保存手机相册。

云端保存成功后才保存相册。因此相册权限失败时，云端历史和用量已经更新。前端未上传原图到 MinIO，也未传 `originalPhotoUrl`，当前标准流程只存成品。

### 六寸排版

前端要求已登录 → `/api/photo/generate-layout` → 后端在 openid 对应用户存在时检查并增加用量 → 调 Python `/generate_layout_photos` → 前端写文件并保存相册。

排版照没有写入云端历史；用量在 Python 生成前增加，生成失败也会消耗一次。该接口的 openid 是可选参数，传空或无法找到用户时仍继续生成。

### 配额规则

`UserDailyUsageServiceImpl` 以用户和服务端当天日期统计：

- 当天广告观看数少于 5：允许保存次数为 `5 + adViewCount`。
- 当天广告观看数达到 5：允许不限次数保存。
- 单图和排版照共用 `saveCount`。
- 返回业务码 `4031` 时，前端提示观看激励视频。
- 完整观看后，前端调用 `/api/user/recordAd` 增加广告计数，再重试保存。
- 广告位优先从 `/api/app/config` 获取，取不到则使用前端默认值。

后端目前信任前端的广告记录请求。配额采用“查询、判断、写回”步骤，没有事务或原子条件扣减；Mapper 中有自增 SQL，但 Service 当前没有使用。

## 6. 历史与文件生命周期

- `t_user`：微信 openid、昵称、头像及时间；当前 UI 固定显示“微信用户”，没有资料编辑流程。
- `t_photo_history`：所属用户、成品 URL、可选原图 URL、底色、创建时间、逻辑删除标识。
- `t_user_daily_usage`：用户、日期、保存次数、广告次数；用户与日期有唯一索引。
- MinIO 文件路径为 `yyyy/MM/dd/UUID.png`，新建桶时设置公开读权限。
- `/api/history/list` 通过 openid 查用户，返回未逻辑删除的全部记录，没有分页或七天条件。
- `/api/history/{id}` 仅按 ID 逻辑删除，不检查所属用户，也不立即删除对象文件。
- `HistoryCleanupTask` 每天服务器时间零点查询七天前的记录，删对象，再物理删除数据库记录。
- 清理查询使用 MyBatis-Plus 普通 `selectList`，会受到 `@TableLogic` 过滤：用户提前逻辑删除的记录可能不再进入定时清理，造成对象残留。
- 过期清理依赖每日任务，并不是精确七天到期；文件删除失败只记录日志，随后仍删除数据库记录，缺少重试入口。

## 7. 接口映射

Java 接口统一返回 `{ code, message, data }`；成功业务码为 200。

| 方法 | Java 路径 | 用途 / 下游 |
| --- | --- | --- |
| GET | `/api/app/config` | 返回激励广告位 ID |
| POST | `/api/user/login` | code 换微信身份并注册或登录 |
| GET | `/api/user/usage` | 查询或新建当日用量；当前前端未调用 |
| POST | `/api/user/recordAd` | 增加广告观看数 |
| POST | `/api/photo/generate-idphoto` | multipart 文件 → Python `/idphoto` |
| POST | `/api/photo/add-background` | 表单 Base64 与颜色 → Python `/add_background` |
| POST | `/api/photo/generate-layout` | 表单 Base64 与尺寸 → Python `/generate_layout_photos` |
| POST | `/api/history/save` | JSON → 存文件、写历史、增加用量 |
| GET | `/api/history/list` | 查询用户历史 |
| DELETE | `/api/history/{id}` | 逻辑删除记录 |

没有统一异常处理器。Python 调用主要根据 HTTP 状态判断成功，未检查返回 JSON 的业务 `status`，可能将图像引擎的业务失败包装为 Java 成功响应。

## 8. 已定位的迭代注意点

以下为代码阅读结论，尚未修改实现：

1. **接口地址重复前缀**：`app.js` 默认 `baseUrl` 带 `/api`，每个请求又拼 `/api/...`，按当前配置会形成 `/api/api/...`。配置后端域名时需先统一约定。
2. **登录后丢编辑结果**：编辑页保存时跳到“我的”，登录后回首页；没有保存草稿或恢复原编辑页的机制。
3. **排版广告重试走错分支**：单图和排版共用广告弹窗，但广告完成后固定调用 `savePhoto()`，原先的排版操作不会恢复。
4. **身份与权限不完整**：openid 直接由客户端提交；删除仅凭 ID；广告记录可直接请求，排版接口还允许无有效用户时继续。
5. **历史清理存在遗漏**：逻辑删除与定时任务的查询方式冲突，可能留下照片文件。
6. **配额和保存缺少一致性保障**：并发更新可能丢计数或越过限制；排版失败消耗配额；存储、历史写入与用量更新缺少补偿。
7. **异常与加载态需统一**：相册保存失败分支引用未定义的 `data.message`；`wx.login` 没有 fail 回调；部分网络请求失败没有提示。上传完成时还会关闭换色请求刚打开的全局 loading。
8. **编辑并发只覆盖换色**：重新抠图没有请求序号保护，旧请求可能覆盖新尺寸；处理中也未清空旧成品，保存可能使用旧图。
9. **照片格式声明需统一**：本地图和 MinIO 均写为 `.png`，但本地 Python 文档称换色返回 JPG，且页面按 JPEG 预览。后续读取个人 Python 仓库确认：不传 `kb` 时实际编码为 PNG，传 `kb` 时转为 JPEG；当前 Java 未传 `kb`。仍需确认线上部署版本一致。
10. **日志包含图片数据**：`LogAspect` 完整序列化非文件参数和响应，可能把照片 Base64、openid 和登录 code 写入日志，增加日志体积及照片留存范围。
11. **页面说明与行为不一致**：“清空历史缓存”仅清本地 Storage 并保留 openid，不删云端历史或临时图片；协议称可以清空云端记录，与实现不一致。首页“不留痕”文案也与云端成品留存不一致。

## 9. 开发边界与后续入口

- 修改页面交互和编辑流程，主要从 `mini-program/pages/edit/edit.js` 与同名 WXML/WXSS 进入。
- 修改处理模型、输出尺寸/格式和图像参数，从 `PhotoController`、`PythonApiServiceImpl` 及独立 Python 服务进入。
- 修改广告与额度，从 `UserController`、`UserDailyUsageServiceImpl` 和编辑页保存回调进入。
- 修改历史保留与删除，从 `PhotoHistoryController`、`HistoryCleanupTask`、`MinioStorageServiceImpl` 进入。
- 本地启动依赖真实的小程序 AppID/Secret、Java/Maven、MySQL、MinIO、HivisionIDPhotos；仓库当前使用占位配置，未提供 Docker 编排或独立环境配置。
- 仓库没有自有自动化测试或 CI 工作流；小程序 `npm test` 只是默认失败占位脚本。
- 仓库同时提交了小程序 `node_modules` 和 `miniprogram_npm`；后续升级依赖时需关注源码、锁文件与开发者工具构建产物的一致性。
- `backend/update_js.py` 是硬编码旧电脑路径的历史修改脚本，不属于服务运行链路。

建议迭代顺序：确认运行环境并打通实际制作链路 → 修复登录草稿、广告重试、删除清理和身份校验 → 再扩展新的照片工具能力。

## 10. Python 公开源码核对补充

用户指定的图像处理项目为上游 [Zeyi-Lin/HivisionIDPhotos（master）](https://github.com/Zeyi-Lin/HivisionIDPhotos/tree/master)，后续开发以此作为 Python 服务的源码参考；本项目 README 也指向该上游。已直接读取上游 `deploy_api.py`、`hivision/creator/choose_handler.py` 和 `docker-compose.yml`，确认当前 Java 调用的接口及参数能够对应上。

个人账号下的 [weijunli-No1/HivisionIDPhotos](https://github.com/weijunli-No1/HivisionIDPhotos) 是该上游的 Fork。此前读取了个人 Fork 的推理主流程、抠图实现和图像编码函数，这些内部实现细节暂作为辅助参考；后续修改涉及这些模块时应再核对上游对应版本。没有把第二个仓库克隆进当前项目。

- `deploy_api.py` 使用 FastAPI，对外接口与 Java 调用的 `/idphoto`、`/add_background`、`/generate_layout_photos` 对应。
- Java 生成证件照时只传原图、宽高和 `hd=true`，因此按读取到的 Python 接口默认值使用 `modnet_photographic_portrait_matting` 抠图和 `mtcnn` 人脸检测。
- `hivision/creator/__init__.py` 的 `IDCreator` 依次进行输入缩放（最长边 2000）、抠图、美颜处理、人脸检测、可选对齐、裁切和图像调整，产出标准图与高清图。美颜参数默认为零，Java 当前未开放调整参数。
- `hivision/creator/human_matting.py` 使用 ONNX Runtime 加载本地模型权重；还支持 `hivision_modnet`、`rmbg-1.4`、`birefnet-v1-lite` 等分支。默认 MODNet 分支使用 CPU 推理；`RUN_MODE=beast` 时保留推理会话，其他模式用后释放会话。
- 模型权重目录在 Git 树中仅有 `.gitkeep`，读到推理代码不代表权重已安装或服务已运行。
- `deploy_api.py` 直接启动监听 `8080`；Compose 将 `app.py` 的交互界面映射为 `7860`，API 服务映射为 `8080`。当前 Java 配置为 `127.0.0.1:7860`，与这份公开部署配置的 API 端口不一致；实际服务器是否做过端口映射、反向代理或源码修改尚未验证。
- `/idphoto` 捕获人脸错误后返回 HTTP 成功响应中的 `status=false`，进一步证实 Java 不能只判断 HTTP 状态码。
- `hivision/utils.py` 的默认图像编码函数使用 PNG，指定 `kb` 的压缩函数使用 JPEG。当前 Java 没有传 `kb`，按这份源码会取得 PNG。

以上确认的是用户指定的上游项目、公开接口及配置对应关系。线上实际部署的提交版本、自定义配置和运行状态仍需结合部署环境核验。
